# 个人中心与现场报到设计

日期：2026-08-18

## 1. 目标与范围

本功能在现有实训营网站、报名审核后台和统一数据库内完成，不建设独立报到服务。目标包括：

1. 将学员个人中心整理为“个人信息、账号安全、报到二维码”三个清晰栏目；
2. 统一报名审核状态的用户侧名称和展示逻辑；
3. 允许学员维护可编辑的个人信息，同时保护登录手机号和审核记录的一致性；
4. 仅向已录取学员签发报到二维码；
5. 为工作人员提供扫码核验、确认报到、重复扫码提示和有审计记录的撤销功能。

本期不包含座位分配、住宿预订、缴费、证书核销、门禁控制和多场次分别签到。

## 2. 总体方案

采用现有“独立项目＋模块化单体＋统一数据库信息真源”架构，在三个现有应用边界内扩展：

- 学员端 `apps/web`：个人中心、个人信息编辑、报到二维码展示；
- 管理后台 `apps/admin`：现场扫码、报到核验、确认与撤销；
- API `apps/api`：个人资料更新、报到凭证签发与核验、报到状态变更、审计记录。

前后端继续通过版本化 API 和共享 contracts 解耦。二维码中不存放姓名、手机号、单位、报名编号或应用主键，只存放随机、不可枚举的报到凭证。所有身份与录取状态均由后台实时查询确认。

## 3. 学员个人中心

### 3.1 页面结构

桌面端采用左侧栏目导航、右侧内容区；移动端将左侧导航改为顶部标签。栏目固定为：

1. 个人信息；
2. 账号安全；
3. 报到二维码。

页面沿用实训营网站现有蓝色体系，使用紧凑的机构类信息系统排版：白色卡片、细边框、小圆角、克制阴影和统一的字段行距，不使用大面积渐变、超大字号或装饰性图形。

### 3.2 个人信息

个人信息采用一项一行的“字段名＋字段值”布局，例如：

- 姓名　郑博元
- 手机号　+86 188 1113 2625
- 单位　中国科学院大学
- 培养单位　中国科学院物理研究所
- 身份　研究生
- 专业或研究方向　……
- 报名状态　待审核

标题“个人信息”右侧设置“编辑信息”按钮。点击后进入编辑状态或专用编辑页。手机号同时是登录账号，只展示，不允许在个人信息中修改；后续如需换号，应作为独立的账号安全流程建设。

可编辑内容来自报名表中的个人基础信息。修改应记录更新时间；已提交后的变更不能覆盖历史报名快照。审核人员查看申请时应能获得当前资料，并保留提交时的不可变版本用于追溯。

### 3.3 账号安全

账号安全独立于报名资料，包含：

- 修改密码；
- 通过验证码重置密码；
- 退出当前账号；
- 修改密码后退出全部设备。

表单使用标准纵向布局，输入框、标签、说明和操作按钮对齐，不使用浏览器默认未样式化控件。

### 3.4 报到二维码

报到二维码栏目对所有登录用户保留导航位置，以避免录取后页面结构变化；栏目内容按状态控制：

- `admitted`：显示二维码、姓名、单位、报到说明和当前报到状态；
- 其他状态：不签发二维码，显示“录取后开放报到二维码”；
- 已报到：继续显示二维码，并明确显示“已报到”和首次报到时间。

二维码凭证由服务端签发。前端不得自行拼接应用 ID 或用户 ID 生成二维码。

## 4. 报名审核状态

数据库状态不变，统一用户侧文案如下：

| 系统状态 | 用户侧名称 | 含义 |
| --- | --- | --- |
| `draft` | 草稿 | 尚未正式提交 |
| `submitted` | 待审核 | 已提交，尚未开始审核 |
| `reviewing` | 审核中 | 工作人员正在审核 |
| `needs_supplement` | 待补充材料 | 需按要求补充指定信息或附件 |
| `admitted` | 已录取 | 报名审核通过 |
| `waitlisted` | 候补 | 进入候补名单 |
| `rejected` | 未录取 | 本次未录取 |

个人中心同时展示：

- 当前状态：以状态标签突出显示；
- 审核流程：说明可能经历的完整路径；
- 状态时间线：仅展示已经真实发生的状态、时间和面向学员公开的原因。

完整路径为：

`草稿 → 待审核 → 审核中 → 已录取／候补／未录取`

如需补充材料：

`审核中 → 待补充材料 → 审核中`

## 5. 报到凭证与数据模型

新增报到凭证和报到记录，概念上分离，避免二维码安全凭证与业务结果混在同一字段中。

### 5.1 报到凭证

每名已录取学员拥有一个活动范围内有效的随机凭证。数据库只保存凭证摘要，不保存可直接复制使用的明文。凭证应具备：

- 足够随机，不能根据用户、手机号或报名编号推算；
- 仅适用于本次实训营；
- 可被后台撤销或重新签发；
- 学员失去录取资格时立即不可用；
- API 响应和二维码页面禁止公共缓存。

### 5.2 报到记录

每名学员最多存在一条有效报到记录，至少包含：

- 学员或申请标识；
- 首次确认报到时间；
- 确认报到的管理员；
- 当前是否有效；
- 撤销时间、撤销管理员和撤销原因；
- 最近更新时间。

重复扫码不得创建第二条报到记录。

### 5.3 审计记录

以下操作必须进入现有后台操作记录：

- 签发或重新签发报到凭证；
- 确认报到；
- 重复扫码查看；
- 撤销报到；
- 重新确认报到。

审计信息至少包括管理员、时间、对象、操作类型和撤销原因。日志中不得记录二维码明文凭证。

## 6. 后台扫码报到

### 6.1 页面入口

管理后台增加“现场报到”一级入口。页面提供两种核验方式：

1. 调用设备摄像头扫描二维码；
2. 摄像头不可用时，手动输入报到码。

仅具有统一管理员权限且账号处于启用状态的工作人员可使用。

### 6.2 扫码结果

凭证核验成功后，后台显示完成现场核验所需的最小信息：

- 姓名；
- 手机号；
- 单位；
- 培养单位（如有）；
- 报名状态；
- 报到状态。

未录取、凭证失效、凭证不存在或账号停用时，不显示个人资料，只返回明确错误状态。

### 6.3 确认与重复扫码

未报到的已录取学员显示“确认报到”按钮。确认成功后立即显示报到时间和操作管理员。

同一二维码重复扫码时：

- 不创建重复记录；
- 显示“已报到”；
- 显示首次报到时间；
- 显示首次操作管理员；
- 不再提供普通确认按钮。

### 6.4 撤销报到

已报到记录提供“撤销报到”操作。管理员必须填写撤销原因后才能提交。撤销后：

- 原首次报到信息继续保留；
- 记录标记为已撤销；
- 保存撤销操作人、时间和原因；
- 再次扫码时可重新确认报到，并形成新的审计事件。

## 7. API 边界

建议新增以下职责明确的接口，实际路径沿用项目既有 `/api/v1` 风格：

- 学员读取和更新个人资料；
- 已录取学员获取自己的报到二维码数据；
- 管理员核验报到凭证；
- 管理员确认报到；
- 管理员撤销报到；
- 管理员查询报到记录。

核验与确认必须分成两个操作：扫码只读取，不应自动报到，工作人员必须检查信息并主动点击“确认报到”。所有写操作使用防重复提交和并发控制；重复请求返回当前记录，而不是产生重复数据。

## 8. 错误与边界处理

- 未登录：不返回个人中心和二维码数据；
- 未录取：不签发、不返回报到凭证；
- 录取状态被撤销：已有凭证即时失效；
- 无效或过期凭证：后台不泄露是否存在对应手机号或用户；
- 重复确认：返回已报到状态及首次报到信息；
- 撤销未填写原因：拒绝提交；
- 并发扫码：数据库唯一约束和事务保证只产生一条有效报到记录；
- 摄像头权限被拒绝：允许手动输入报到码；
- 网络失败：前端不显示成功状态，允许安全重试。

## 9. 验证要求

### 9.1 自动测试

- 状态文案和个人信息逐行布局组件测试；
- 个人资料编辑权限和历史快照测试；
- 未录取用户无法获取二维码；
- 已录取用户能够获取二维码；
- 无效凭证不能枚举个人信息；
- 首次确认、重复确认、撤销和重新确认的集成测试；
- 两名管理员并发确认只能产生一条有效记录；
- 所有确认和撤销均生成审计记录；
- 管理员与普通学员的访问控制测试。

### 9.2 页面验收

- 桌面端个人信息一项一行，标签和值在同一水平线上；
- 移动端字段行可自然换行，不产生横向滚动；
- 三个栏目切换清晰，账号安全控件样式统一；
- 非录取用户不显示二维码；
- 已录取和已报到状态清晰可辨；
- 摄像头扫码、手动输入、确认、重复扫码和撤销流程均可完成；
- 页面刷新后报到状态与数据库一致。

## 10. 实施边界

本功能应在现有脏工作区中采用小步、定向修改，不覆盖现有报名表、内容真源、单位名录和页面排版改动。数据库迁移、contracts、API、学员端和管理后台按依赖顺序实施，并分别验证后再做完整端到端验收。
